# 爱多格双二维码与正式小红书入口

当前顾客入口保持基础版；小组件0.1.1仍在官方审核中，微信体验H5白页尚未解决。本文件说明取得并验证正式入口后的切换方法，不表示微信链路已通过。后台入口配置不改小组件代码包，也不需要因此撤回或重提现有审核。

## 同一入口用于后台全部操作

`lib/share-entries.ts`从可信服务端配置计算`shareEntries`，仅由已登录管理员的dashboard接口返回。QuickAdmin的二维码一、打开、复制和顶部顾客页共用同一URL；二维码二始终保留点评／美团／抖音基础入口。旧服务端未返回该字段时也保持基础版。

不修改旧的`publishing/officialReady`，不借用门店主页链接，也不触发下载、发布或素材归档。配置不涉及数据库迁移，独立的0008关联模块仍未接入生产。

## 何时可以切换

先在实际官方后台确认正式版已上线，取得小红书生成的分享短链，并在真实手机验证它属于爱多格自己的WidgetID：微信扫码进入、图片和当前文案带入顾客自己的编辑页、修改与取消返回均可用。Android和iPhone的验证分别记录，不能用体验版、格式检查或本地测试替代。

目前只接收无query／fragment的`https://xhslink.com/...`或`https://www.xhslink.com/...`短链。链接格式检查不能证明归属、正式上线或微信可用；若实际官方分享链接不符合已支持格式，先核实官方合同再适配，不删参数或自行拼造链接。

## 生成与链接对应的立牌

在后端项目目录使用：

```sh
node scripts/build-widget-share-code.mjs \
  --url '实际已验证的官方短链' \
  --app-id '自己的24位WidgetID' \
  --out '/绝对路径/一个新的输出目录' \
  --confirmed-entry
```

`--confirmed-entry`仅记录操作者已完成上述实际验收，不是脚本自动检验微信或平台归属。输出包含可编辑HTML、1920×2640立牌PNG、独立二维码PNG及生成记录，使用原爱多格Logo和真实微软雅黑。脚本复用后台相同的URL校验与命名逻辑，文件名为`xhs-widget-<原始URL的SHA256前16位>.png`。

脚本只创建新输出目录，拒绝覆盖已有目录，不上传、不改`public/codes`或线上配置。内部版式检查用`--draft`替代`--confirmed-entry`：会加入“测试样张 · 勿给顾客”标识、`-draft`文件名及`deployable:false`记录；后台不接受该文件名作为正式立牌。

把正式立牌和独立二维码分别回读，确认均与原始分享短链完全一致；检查字体、Logo和版式，再把正式PNG复制到本项目Studio的`/aidog-share/codes/`或GitHub的`/adog-xiaohongshu/share/codes/`。确认线上响应确实是当前PNG，并用新立牌扫码复核。不要覆盖仍在使用的基础版立牌。

## 私有运行配置

实际验证和立牌发布完成后，在Studio既有私有运行配置中设置：

- `XHS_WIDGET_APP_ID`：自己的24位小组件编号。
- `XHS_WIDGET_CUSTOMER_URL`：上述原始官方短链，不做规范化或删改。
- `XHS_WIDGET_CUSTOMER_ENTRY_VERIFIED=true`：实际验收完成后才开启。
- `XHS_WIDGET_CUSTOMER_POSTER_URL`：对应PNG的完整HTTPS地址；限上述两个项目位置，文件名必须与当前短链的摘要相符。

缺少或无效的开启标记、WidgetID、短链时，二维码一保持基础版。正式短链可用但没有匹配立牌时，后台显示“立牌待更新”，不会提供旧小红书或点评立牌。文件名校验不检查远端PNG内容或可访问性，发布前的HTTP及二维码回读仍须实际完成。

让新配置按既有部署流程生效后，重新载入后台，核对显示、复制、打开和立牌四处一致，再发给顾客。要回退基础版，移除验证标记并按同一流程生效；二维码二无需更改。不得把私有运行文件、账号密码或推送密钥提交到GitHub。
